# CI qualification and latency evidence

This is the implementation and evidence ledger for [clonk-org/clonk-rs#1886](https://github.com/clonk-org/clonk-rs/issues/1886). All twelve children are in scope, including the three previously tracked issues. The goal is faster qualification with the same source identity, test inventory, parity checks, coverage floor and shipped runtime settings. Local measurements and historical Actions results below are evidence for particular changes; they do not establish the revised workflow's cold-build latency or p95. The curated numbers, source URLs and raw-evidence SHA-256 hashes are in [ci-qualification-baseline.json](ci-qualification-baseline.json).

**Source identity and reuse policy.** There is no cross-commit speculative promotion. `CARGO_PKG_VERSION` is a real runtime input in [version.rs](../crates/clonk-core/src/version.rs), and release notes and the selected main parent also change generated release inputs. Equivalence would have to establish source SHA/tree, content gitlink, dependency graph, generators, golden/reference data, workflow and build recipes, Rust/LLVM, target/profile/features/flags, environment and native tools/SDKs. Changed or unknown values require normal compilation and qualification. This policy does not rely on an unproven claim that every application binary embeds its Git commit.

Build-once means one exact candidate's producer outputs are handed to its own consumers. [Prebuild manifests](../scripts/release-prebuild-manifest.py) record actual producer operation, profile, target, features, environment, compiler/native-tool identities, payload sizes/hashes and parent relationships. Packaging validates the identity before copying; macOS records fusion/signing rather than attributing its final bytes to a source slice. [Device-loss](../scripts/run_device_loss_probe.py) and [software-presentation](../scripts/run_software_presentation_smoke.py) helpers validate the prebuilt payload and execute it; local build mode remains available. Vulkan/GL, DX12 and Metal qualification and shipped MSVC import/CRT validation remain required.

The post-landing qualification receipt binds the complete committed tree, clean materialized content, source run/attempt, required successful jobs and immutable GitHub artifact digests. Its writer runs before Landing completes; its resolver requires the completed Landing gate and child inventory. It cannot borrow an unrelated green job. Exact identity permits reuse after landing; missing, expired, corrupt or incomplete evidence triggers the normal path. Coverage merge/floor validation still runs when its qualified fragments are reused, and trusted-main warmers preserve future dependency acceleration.

Stale release refresh is limited to a same-repository automation-owned single generated commit changing `Cargo.toml`, `Cargo.lock` and `CHANGELOG.md`. It keeps the existing PR, version and original operation clock, regenerates notes against selected main and verifies main ancestry. A unique scratch ref is seeded at selected main; its Git fast-forward transports only the generated release changes. GraphQL `updateRefs` then compares the observed candidate and scratch heads atomically, replacing the candidate and deleting the scratch ref together. A changed head prevents both operations; the existing candidate is never temporarily reset to main. Bounded cleanup retains a receipt if scratch-ref removal remains unresolved. Older reruns cannot rewind a newer parent. Landing requires the generated commit's sole parent to match its queue base; another main race requires refresh. No Workflows permission was granted; actual API authorization with the existing release App token remains a live-validation requirement. These guards do not authorize direct pushes to main.

**Cache inputs and retained gates.** [Workspace-cache action](../.github/actions/workspace-cache/action.yml) checks source bytes, including compiler dep-info inputs, Cargo fingerprints, manifests/lockfile, profile/features/flags, toolchain, content and relevant environment. Each checkout owns its target directory. Unverified workspace fingerprints are removed before Cargo; generated, external or otherwise unverifiable inputs require rebuilding. The restore prefix normalizes workspace package versions only to locate reusable dependency inputs. Raw manifest/source bytes still invalidate changed workspace units; prefix normalization is not binary equivalence.

Preparation removes old raw profiles, merged profile data, LCOV/JUnit/coverage reports and nextest outputs before measurement. Required coverage fragments are run-scoped artifacts, not compiler-cache contents. Optional cache restore/save failures do not replace a gate failure or hide an invalid identity. Only trusted main publishes authoritative caches. Retention owns `landing-linux` and `coverage-linux` keys only, caps them at **4 GiB total and at most two entries per lane**, reserves each lane's newest entry when it fits, and leaves unrelated caches and artifacts alone.

The final pre-deployment repository inventory contained 54 caches totaling 10,180,739,840 compressed bytes, including 3,339,796,564 bytes in the two legacy Linux `full-parity` entries. The new ledger-backed targets replace that transport; they are not twelve per-shard target archives. The owned-lane cap does not cap the repository's other caches. Live validation must measure archive sizes, restore/save overhead and eviction effects on Windows and native-oracle caches before claiming a net benefit.

Each of eight workspace-input preparation job roles emits reused/invalidated unit counts through `--github-output`, followed by a successful workflow receipt step displaying its state. `warm` means at least one verified workspace unit was reused and none invalidated; `cold` means none reused; `unknown` means mixed reuse/invalidation. This describes the checkout's compiled workspace inputs, not third-party dependency-cache hits or whole-candidate temperature. Missing or conflicting receipts keep the candidate's state `UNKNOWN`.

Coverage collectors and the no-run warmer export the actual pinned `cargo-llvm-cov 0.8.7` environment, including its compiler wrapper context, then invoke pinned `cargo-nextest 0.9.91` directly. They do not nest `cargo llvm-cov nextest` inside its own exported wrapper. A local isolated zero-dependency probe proved that `--no-run` executed no test body and wrote no JUnit; its two discovery raw profiles were then cleaned. The real run produced three raw profiles, LCOV with 11/11 hit lines and positive line counters totaling 14, and JUnit with one test, zero failures and zero errors. Nextest's JUnit was at workspace `target/nextest/ci/junit.xml`, independently of `CARGO_TARGET_DIR=target/coverage-build`; production reset, retention and upload use that observed location. All eleven coverage contract guards passed. This checks pinned instrumentation/JUnit/no-run behavior; it does not establish full-workspace coverage, the retained floor or live cache handoff.

Exhaustive qualification still has **18 Linux rows, two Windows smoke rows and twelve coverage fragments**. The LCOV line floor is **79.45%**, with the same exclusion expression; the historical LLVM JSON-to-LCOV macro-expansion accounting adjustment does not permit less coverage. The seven public artifact names are `desktop-linux`, `desktop-windows`, `desktop-macos`, `components-desktop-linux`, `components-desktop-windows`, `components-desktop-macos` and `release-tool`. Internal manifests, receipts, fragments and probe reports do not enlarge that public allowlist. Parity, snapshots, compatibility, recording, packaging, native material-order oracles and GPU recovery gates remain.

**Deliberate runner allocation.** The candidate envelope is:

| Release work | Capacity | Scheduling rule |
| --- | ---: | --- |
| Exhaustive Linux | 5 | All 18 rows retained; historically longest rows requested first. |
| Coverage | 6 | All 12 fragments retained; historically longest rows requested first. |
| Platform producers/packages/probes | 4 | Linux 1, Windows 1, macOS 2; each platform validates, builds runtime(s), then its tool, then packages/qualifies. |
| Windows smoke | 2 | Both rows retained. |
| Independent native checks | 3 | Existing native qualifications retained. |
| Total | **20** | Ordinary candidates retain Linux capacity 17 plus two Windows rows. |

The tool's dependency on its own runtime is an intentional capacity edge, not a claim that the tool consumes runtime data. This starts the expensive Windows/macOS runtimes early while keeping the seven producers within four lanes. A package waits only for its own platform inputs; unrelated platform completion is no longer a barrier. Candidate-priority concurrency makes ordinary post-landing diagnostics yield to Landing. Queue build concurrency remains one.

Authoritative content/Linux/Windows/coverage/recording cache publishers remain noncancelled, bounded jobs outside this candidate envelope. They and other repositories can occupy the account pool, so the table is not an account-wide occupancy guarantee. Live validation must check queue wait, starvation and eventual cache publication. Matrix declaration order is a scheduling request, not a guarantee of GitHub start order.

In the historical [release run](https://github.com/clonk-org/clonk-rs/actions/runs/37379197541), observed concurrency peaked at 20 and stayed there for 446s. Windows runtime waited 305s from job creation to start; qualification waited 746s behind the broad Linux dependency. Linux/macOS packaging inputs were ready 707s/268s before the all-platform barrier released them. Created-to-start intervals include provisioning and scheduling; they cannot be partitioned into runner-pool and dependency delay from these APIs alone.

Using historical job durations and longest-first scheduling, Linux capacity 5 models 1,585s and coverage capacity 6 models 1,386s. Platform chains model 933s Linux, 1,472s Windows and 1,285s macOS before the new bounded GPU path. Adding bounded probes, identity checks and a tail gives approximately **1,635s**, versus the historical release clock of 1,931s. A 4/4 Linux/coverage split models 1,977s/1,941s even before the other paths, so that alternative was rejected. None of these are measured revised-workflow durations, cold-build guarantees or percentile estimates.

**Clocks and historical populations.** Preparation's operation clock is dispatch/workflow creation to the new release PR's API creation time. Publication's operation clock is the qualified release PR's merge time to release publication. Workflow elapsed and qualification execution are reported separately; they do not replace either operation's two-minute objective. A PR from another run, a reused/already-published release or a missing operation anchor is excluded from operation percentiles. Reruns retain original creation and prior attempts; a later success does not erase failed history. Functional failure remains failure, while a clock miss emits an advisory warning.

**Measured local product and test scheduling changes.** A fixed silent options capture showed 753 classic group lookups per boot across four independent boots. Directory enumeration/sorting accounted for 6.753s of a 16.590s instrumented probe; wildcard lookup itself accounted for only 8.470ms. `sort_by_cached_key` now computes rank and ASCII lowercase once per entry, preserving fresh directory I/O, descending first wildcard rank, raw-byte directory tie order and stable writer equal-name order. The tests pin the instrumented C++ oracle's `C4Group.cpp:2300–2336` contract, filename CRCs and serialized offsets/bytes. Two regression tests were witnessed red at 46 rank evaluations instead of 24, then green; the 407-test resources/FFI suite passed with no skips and focused clippy was clean.

On a Ryzen 9 9900X host with 63,365,024 KiB RAM, Rust 1.98.1/LLVM 22.1.8 and isolated ordinary/LLVM targets, the same warm capture improved **3.194s → 2.789s ordinary** and **16.750s → 10.045s instrumented**. Compilation is excluded; each figure is a focused local sample, not a shard-wide or hosted-runner speedup. The current app inventory remains 804 tests. Baseline profiling used temporary timers; no overall RAM improvement is claimed. Timers were removed from the retained source.

For ClonkMars on four physical cores, the unchanged strict reference measurement improved from 482.90–518.17ms to **364.463ms**, with stage time 362.527ms. The full retained fixture took 10.921s. Instrumented reference latency was 1.936s: the pre-existing coverage configuration does not enforce the ordinary one-second timing threshold, so that run establishes functional behavior only. No threshold, fixture initialization or independent-state requirement was weakened.

The isolated nextest 0.9.91 scheduling pair ran the same twelve tests at `-j4`: **25.272s → 13.101s**, a 48.16% elapsed reduction. Median per-test slowdown was 1.19%, maximum 4.59%. Peak aggregate RSS increased **740 → 1,415 MiB** and PSS **734 → 1,365 MiB**, with one versus two concurrent test processes. This is an explicit memory/time tradeoff. Both timing contracts remain exclusive; observed ordinary lobby/reference samples were 182.96ms/483.43ms before scenario work. Default many-core local reservations, retries and timeouts are retained.

A bounded decoded-image cache was trialed and removed. After sorting, it produced only a small capture improvement, no ClonkMars reference improvement (364.463ms without versus 366.990ms with it), and approximately 65.9 MiB additional ordinary host-fixture peak RSS. No image or directory-listing cache is retained.

The controlled historical audio-window comparison used [A: 7b6752938](https://github.com/clonk-org/clonk-rs/commit/7b6752938c6d2c31d7a291bed667e16cc18630f5), [B: 3e2620aa1](https://github.com/clonk-org/clonk-rs/commit/3e2620aa1d50ca43885a73174b9f6f4ced712f7d), then returned A, with identical historical lock/content, compiler, instrumentation, runner and silent canonical fixture. Execution was **15.898s / 15.776s / 15.715s**; compilation was separately **168.00s / 30.82s / 33.32s**. B was 0.193% faster than the mean A samples, so neither the reported 2–3× slowdown nor the later approximately 17% window reproduced here. Sound, music, menu audio and voice were disabled. The historical inventory was 778 tests; this is not an audio-enabled test or the original Azure host. The initial 420s bound interrupted B; an authorized extension completed B and returned A in 96.35s. Scratch targets were isolated and removed. Sorting fixes a measured present bottleneck; it does not prove the historical onset's cause.

**Windows evidence and infrastructure decision.** In the [native Windows runtime job](https://github.com/clonk-org/clonk-rs/actions/runs/37379197541/job/111996550058), 26 workspace crates and zero third-party crates compiled after dependency-cache hits. Cargo took **828s (13m48s)**; the encompassing build step took 862s including index/fetch work. Final application linking reported **357.029s total, 355.583s ThinLTO**. This identifies linker work without pretending the remaining Cargo time is a clean compile-only measurement: dependency scheduling, code generation and other links overlap. A later native-tools run also took 900s for its runtime. Existing dependency reuse alone cannot guarantee a cold runtime under ten minutes.

Retain standard Windows capacity and current billing. If an owner authorizes a matched capacity experiment, use four runs of at most 20 minutes on x64 Windows `windows_8_core` (8 vCPU, 32 GB RAM), maximum concurrency one, matching exact SHA/content, Rust/LLVM, target, profile, flags, static CRT and unwind. GitHub lists **$0.042/min**, yielding a **$3.36 compute ceiling**; storage and plan fees are outside that ceiling, and partial minutes round up. Larger runners require Team/Enterprise Cloud and owner-configured capacity/access. No runner or billing change was made. [Official pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing), [specifications](https://docs.github.com/en/actions/reference/runners/larger-runners), [availability](https://docs.github.com/en/actions/concepts/runners/larger-runners) and [capacity management](https://docs.github.com/en/actions/how-tos/manage-runners/larger-runners/manage-larger-runners) are the sources. Cold provisioning and a matched warm/cold pair remain part of the experiment, not an assumed gain.

**Completion evidence.** The focused results above do not replace the required gates for the revision being shipped:

```sh
cargo nextest run --workspace --no-fail-fast
cargo clippy --profile test --workspace --lib --bins --tests --features xtask/engine-tools --locked -- -D warnings
cargo xtask engine-snapshots verify
cargo xtask parity verify
cargo xtask compat verify
cargo fmt --all -- --check
python3 -m unittest discover --buffer -s scripts/tests -p 'test_*.py'
cargo test -p xtask --features engine-tools --bin xtask-engine-tools --locked
```

The final gate revision and matched revised Actions runs must be recorded on the linked issues/PR. Live acceptance additionally requires exact-candidate producer/consumer digests on every platform; all 18/2/12 inventories and the seven public artifacts; coverage floor success with fresh raw profiles; corrupt/missing cache and receipt fallback; stale release refresh under a main race with the existing App token's API authorization and no Workflows grant; bounded publisher completion; and successful native GPU/runtime qualification. Measure both warm and cold/input-changing paths, retain functional failures and exclusions, and collect the revised recipe's own operation clocks and p50/p95 sample counts before claiming its latency targets are met.
